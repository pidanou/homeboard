# Multi-language Support — Functional Spec

## Core concept

Family Board supports **English, French, Spanish, and German**. Translation happens at compile time via `@inlang/paraglide-js` — every user-facing string is a message key resolved to the active locale's text, tree-shaken per route, with no runtime translation fetch. There is no URL-based locale routing (`/fr/board`); the app is a fully client-rendered SPA (`ssr = false`), so the active locale is resolved and applied programmatically instead.

---

## Locale resolution order

Resolved once on app boot (`(app)/+layout.svelte`'s `onMount`), highest priority last:

1. **Browser default** — if no locale has ever been set client-side, `navigator.language` is checked against the supported set (`en`, `fr`, `es`, `de`); unsupported values fall back to `en`.
2. **`localStorage`** — paraglide's own persistence strategy. Once a locale has been set client-side (by step 1, or by an explicit change), it's read back on every subsequent load, before the profile is fetched — this keeps first paint in the right language without waiting on a network round-trip.
3. **Profile `locale`** — once `loadCurrentUser()` resolves, the account's stored `locale` always wins. If it differs from the currently active locale, `setLocale()` is called to override whatever browser/localStorage guess was showing. This is what makes the choice sync across devices.

Changing the language in **Profile → Language** calls `PATCH /api/v1/profile` with the new `locale`, then `setLocale()` to apply it (which triggers `paraglide-js`'s default `reload: true` behavior — a full page reload re-renders everything, including the layout's own locale-resolution effect, in the new language).

---

## Message keys

- Defined in `web/messages/{en,fr,es,de}.json` — flat, underscore-separated keys valid as JS identifiers (no nested objects, no dots).
- Called from Svelte files via `m.*()` or `msg.*()` (`import * as msg from '$lib/paraglide/messages.js'` — both aliases exist in the codebase; either is fine, pick whichever the file already uses).
- Parameterized messages use named placeholders, e.g. `"taskcard_due_at": "Due {date} at {time}"` → `msg.taskcard_due_at({ date, time })`.
- **Reuse over duplication:** if an English string is character-for-character identical to an already-defined key's value, reuse that key rather than minting a new one (e.g. `msg.dialog_cancel()`, `msg.action_add()` are reused across dozens of dialogs).
- Simple pluralization (member/members, profile/profiles) uses singular/plural key pairs selected by existing JS ternary logic — no ICU plural syntax, since the app's pluralization needs are small and don't warrant the added complexity.

---

## Date and time formatting

All `Intl`/`toLocaleDateString`/`toLocaleTimeString`/`toLocaleString` calls go through `web/src/lib/dates.ts`, which passes paraglide's `getLocale()` instead of `undefined` — so date/time formatting always follows the app's explicit language choice, not the browser's ambient locale (which may differ from what the user picked in-app).

---

## Backend

- `users.locale TEXT NOT NULL DEFAULT 'en'` (migration `000029_user_locale`).
- `AuthService.SetLocale` validates `locale` is one of `en`/`fr`/`es`/`de` (`supportedLocales` in `internal/service/auth.go`), rejecting anything else.
- `GET /api/v1/config` exposes `supportedLocales: ["en", "fr", "es", "de"]`. Note: the frontend's Profile → Language picker currently hardcodes its own `LANGUAGE_LABELS`/`locales` list (from paraglide) rather than reading this endpoint — the two lists must be kept in sync by hand.

---

## What's out of scope

- **Backend error-message i18n.** Toasts that surface raw Go error text (`web/src/lib/api/client.ts`) pass the backend's English error strings through unchanged — localizing those requires an error-code-based i18n layer in the Go service, a separate effort. Only frontend-authored wrapper strings (e.g. "Cannot reach server") are localized.
- **ICU plural rules / gendered grammar.** Only simple singular/plural pairs are supported.
- **RTL languages.** Not needed for en/fr/es; would require layout-direction work if added later.
- **Per-family or per-content locale** (e.g. translating a task title). Locale is a per-user UI preference only.
- **Additional languages beyond en/fr/es/de.** Adding one is mechanical (new `messages/<locale>.json` + entry in `locales` + backend `supportedLocales` map) but not pre-built for.
